# Gemini 1차 작업 — 정보 수업의 페이지 구조

작성일: 2026-09-13 · 상태: 구현 지시서, 앱 미구현
작업 위치: `D:\hack_thon` · 명세 기준: `PRD.md` 9.2~9.4

## 목적과 완료 범위

정보 수업의 여러 단원을 담는 홈과 탐색 구조를 구현한다. 학생이 홈에서 단원을 골라 실제 개념·퀴즈·실습으로 들어가고, 수행평가와 교사 공간에 기존 권한·운영 방식으로 접근할 수 있어야 한다. 임시 서비스명은 `교수평기 올인원`이다.

교사는 차시별 퀴즈·실습 결과와 시간 제한 수행평가 결과를 모아 학생을 이해하려 한다. 평가 기획 기준은 3회 각각 과정 5 + 수행 25, 과정 5 + 수행 25, 과정 5 + 수행 35이다. 이번 작업은 이 기능을 담을 화면 구조까지이다. 차시 저장·점수 환산·공식 성적 반영은 후속 작업이다.

## 시작할 때

1. `AGENTS.md` → `INTENT.md` → `PRD.md`를 읽는다. 기능 요구의 최신 기준은 PRD이며 이 파일은 1차 작업 범위를 정한다. `docs/HACKATHON_HANDOFF.md`도 확인한다.
2. Git 브랜치·원격·미커밋 변경을 확인한다. 기존 변경을 덮어쓰거나 초기화하지 않는다. 현재 `feature/hackathon`은 새 Vercel의 Production 브랜치이다. 현재 작업 내용을 보존한 채 `codex/platform-structure` 작업 브랜치를 사용한다. 같은 이름이 이미 있으면 상태를 먼저 확인하고 기존 작업을 강제로 전환하지 않는다.
3. 현재 사용자·다른 AI가 남긴 문서 및 `tools/firebase-admin.cjs` 변경은 보존한다. `AGENTS.md`, `백업용/`, 원격·배포·Firebase 설정은 수정 대상이 아니다.

## 페이지 구조

```text
교수평기 올인원
├─ 수업 — 학생 기본 홈
│  └─ 단원 개요
│     ├─ 개념
│     ├─ 퀴즈
│     └─ 실습
├─ 나의 기록 — 이번에는 준비 중 안내
├─ 수행평가 — 기존 학생 입장·평가
└─ 교사용 — 기존 교사 인증 후 수행평가 관리
```

상단 주 메뉴는 `수업 / 나의 기록 / 수행평가`로 구성한다. `교사용`은 보조 영역에 둔다. 브랜드를 누르면 수업 홈으로 간다. 단원명 세 개를 최상위 메뉴로 계속 나열하지 않는다. 기존 전체 메뉴를 유지하는 경우 주 메뉴와 같은 경로·선택 상태·평가 잠금 규칙을 사용한다.

| 화면 | 이번에 표시하고 연결할 내용 |
|---|---|
| 수업 홈 | 제목 `정보 수업`, 안내 `학습할 단원을 선택하세요.`. `알고리즘` 주제 아래 현재 세 단원을 표시. 각 단원은 제목·짧은 실제 학습 설명·`단원 보기` 버튼으로 구성 |
| 단원 개요 | 현재 단원명·기존 콘텐츠에 근거한 학습 목표·개념/퀴즈/실습 진입. `수업 > 단원명`의 현재 위치와 수업으로 돌아가기 제공 |
| 개념·퀴즈·실습 | 기존 화면과 기능을 연결. 단원 개요로 돌아가는 경로 및 현재 활동 표시. 일반 화면은 읽기 폭, 실습은 작업 폭 확보 |
| 나의 기록 | `수업 기록 기능을 준비하고 있습니다.`와 `수업으로 이동` 버튼. 학생의 제출 여부를 판단하는 문구·숫자를 표시하지 않음 |
| 수행평가 | 기존 `studentEvalApp.openLobby()` 경로와 입장·평가·제출·결과 표시 유지 |
| 교사용 | 기존 교사 인증·역할 확인 이후 클래스룸 표시. 화면의 목적을 `수행평가 관리`로 명확히 안내하고 기존 학급·회차·채점 기능 유지 |

새 단원은 하나의 목록 정의를 추가해 홈·개요에 반영할 수 있게 한다. 작은 프런트엔드 목록 데이터에 ID·제목·설명·기존 활동 경로만 둔다. 기존 `UNIT_META`와 역할이 겹치는 별도 목록을 만들면 값이 어긋나지 않도록 단일 원본에서 참조한다. 서버 자료 구조를 설계하거나 다른 단원의 콘텐츠를 생성하는 범위는 아니다.

기존 연결값은 유지한다.

| 단원 | 기존 ID / 별칭 | 실습 ID |
|---|---|---|
| 문제 추상화 | `unit1` / `abstraction` | `abstraction` |
| 알고리즘 설계 | `unit2` / `algorithm` | `sandwich` |
| 순서도 연구소 | `unit3` / `flowchart` | `flowchart` |

현재 세 단원은 그대로 진입할 수 있어야 한다. 새 차시 번호·활동 배정·완료 기준은 임의로 정하지 않는다. 후속 구조는 학급 → 단원 → 차시 → 활동이며, 이번 화면의 `알고리즘` 묶음이 새 서버 계층을 뜻하지는 않는다.

## 화면 구성과 디자인

대표 화면인 수업 홈부터 구현한다. 상단 탐색 → 짧은 제목·안내 → 단원 목록 순서로 배치한다. 넓은 창에서는 단원 세 개를 비교하기 쉽게 배치하고 좁은 창에서는 세로로 전환한다. 큰 홍보 영역·성취 그래프·불필요한 배지를 추가하지 않는다. 다른 교사도 단원명과 버튼 문구만으로 이동 경로를 이해할 수 있어야 한다.

기존 글자·간격·색상 규칙을 정리해 재사용한다. 순서도 네 기호의 교육적 색상은 유지한다. 새 UI 프레임워크·제품 빌드 체계를 도입하지 않는다. 고정 사이드바로 순서도 편집 폭을 줄이지 않는다. 상단이 좁아지면 메뉴를 접거나 줄바꿈하고 키보드 초점·현재 메뉴·열림 상태를 표시한다.

후속 교사 기록 화면은 전체 현황 → 학생별 목록 → 제출물 상세 흐름을 목표로 한다. 관련 참고와 이번에 확인한 범위는 PRD 9.4에 있다. 이번에는 수업 관리·학습 기록 관리의 더미 화면까지 확장하지 않는다.

## 코드에서 특별히 확인할 연결

주요 수정 후보는 `index.html`, `css/studio-ui.css`, `js/core/navigation.js`이다. 필요한 작은 목록 데이터 파일과 탐색 관련 검사는 추가할 수 있다. `js/core/classroom.js`, `js/app.js`는 화면 전환 연결에 필요한 부분만 수정한다. 다른 파일 수정이 필요하면 연결 근거를 결과에 설명한다.

* `view-roadmap`을 수업 홈으로 사용할 수 있다. `switchUnit('roadmap')`과 기존 `switchTab('home')` 호출은 새 홈으로 정상 연결되어야 한다.
* 기존 `view-concept`, `view-quiz`, `view-lab`, `view-classroom`, `view-eval`을 유지한다. 새 개요·기록 화면을 추가하면 모든 진입 경로에서 이전 화면을 숨겨 중첩을 방지한다. `switchUnitStep()`와 `showClassroomView()`도 점검한다.
* `isAssessmentLocked()`가 참이면 새 홈·개요·기록·교사용·전체 메뉴·현재 위치 링크에서도 평가를 벗어나지 못하게 한다. 버튼 비활성뿐 아니라 경로 함수에도 같은 제한을 적용한다.
* `pendingAssessmentResume`와 `resumeAssessment()`의 새로고침 복구를 초기 홈 표시가 덮어쓰지 않게 한다. 기존 `#sandwich`, `#abstraction`, `#quiz1`~`#quiz3`, `#step-1`~`#step-5` 등의 진입 경로를 보존한다. 해시 기반 전체 라우터 교체는 필요하지 않다.
* 교사 화면에서 새 화면으로 나갈 때 기존 `stopLiveEvalDashboard()`가 실행되어 구독·타이머를 해제해야 한다. `openClassroomTab()`의 실제 교사 인증을 역할 선택 버튼으로 대체하지 않는다.
* 실습 편집기를 새 컨테이너에 복제하지 않는다. 작성 중 이동·복귀의 기존 상태를 유지하고 평가와 일반 실습의 초안이 섞이지 않게 한다.
* `completedUnitSteps`나 현재 방문 화면을 서버 제출·학습 완료의 근거로 쓰지 않는다. `나의 기록`의 준비 상태에 더미 학생·점수·제출률을 채우지 않는다. 평가 3회가 실제 생성된 것처럼 표시하지 않는다.
* 학생 정보·작업을 `localStorage`에 저장하지 않는다. 로그인·보안 규칙·API·Firestore 구조·채점·시험 시간·AI 도움 범위는 이번 작업에서 바꾸지 않는다.

## 구현과 확인 순서

1. 수업 홈과 공통 탐색을 구현하고 대표 화면을 확인한다.
2. 단원 개요와 기존 활동 진입을 연결한다.
3. 기록 준비 중 화면, 수행평가·교사 진입, 모든 화면의 이탈 처리를 연결한다.
4. 실제 브라우저 조작과 아래 관련 검사를 수행한다. 오류를 수정한 뒤 검증 결과를 기록한다.

이 저장소에는 제품용 `package.json`이 없다. 프레임워크 설치나 `npm run build` 성공을 목표로 삼지 않는다. 문법·참조 확인은 `node tools/check.cjs`를 사용한다. 로컬 미리보기는 `node tools/preview.cjs` 실행 후 `http://127.0.0.1:4173/?demo=1`로 접속한다. 이 서버는 Firebase 초기화를 끄므로 실제 운영 저장 검증으로 보고하지 않는다.

검증 조건:

* 홈 → 세 단원 개요 → 각 개념·퀴즈·실습 → 개요·홈 복귀가 동작하고 화면이 겹치지 않는다. 순서도 다섯 단계와 기존 직접 진입 주소도 확인한다.
* 작성한 실습으로 돌아왔을 때 기존 작업이 유지된다. 평가 중 새 탐색으로 이탈할 수 없고 평가 새로고침 복구가 유지된다. 기존 평가·교사 UI 검사에서 해당 경로를 확인한다.
* 기록 메뉴는 준비 상태를 정확히 표시한다. 교사 인증 전 관리 화면이 노출되지 않고 인증 실패 시 현재 화면을 사용할 수 있다. 교사 화면 이탈 시 구독·타이머가 해제된다.
* 1440·1024·768·390px 폭과 메뉴가 접히는 경계에서 창을 줄였다 늘린다. 주요 버튼·현재 위치·편집 영역의 잘림과 페이지 전체 가로 넘침을 확인한다. 200% 확대와 키보드 메뉴 조작도 점검한다.
* 새 콘솔 오류·스크립트 404가 없는지 확인한다. 기존 검사 파일은 필요한 새 탐색 기대값만 조정하고 평가 보호 검사를 삭제하지 않는다. 실패를 숨기거나 검사 통과만으로 화면 확인을 대신하지 않는다.

운영 계정으로 시험 시작·제출·채점 등 쓰기 검사를 실행하지 않는다. 이번 완료 기준은 로컬 구현과 관련 브라우저 검증이다. 운영 연결 확인은 후속 범위로 구분한다.
